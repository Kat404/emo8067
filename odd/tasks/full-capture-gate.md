# The gate over every capture — memory included

Objective: run every hardware capture of the P80C86A-2 against the emulator,
not a sample of them, and compare the memory the chip wrote as well as the
registers and the flags. Branch: `main`. Delivery: one commit per task, each
leaving the tree green. Test runner: `cargo test --workspace`.

Written 2026-10-23. Continues `odd/tasks/silicon-questions.md`, whose
verification report left this as the one hole it found: the hardware gate
compares registers and flags and **never memory**.

**Risk: item 3** — the oracle's format is a contract between the extraction
script and the gate that reads it, and the gate is what the project trusts
over its own memory, so the change is reviewed on its own and carries an
independent verification.

## Why this and not more

The oracle keeps 2689 cases out of the 646 000 the capture set holds, so
the gate has been reading a sample. The sample is a good one — it takes one
case for each direction of each defined flag — but a sample cannot say that
the emulator's memory matches the chip's, and the verifier had to write a
throwaway probe over all 4000 `8C`/`8E` cases and all 64 000 group-2 cases
to check that. This unit turns that probe into a gate of the project, and
it puts the memory in the comparison.

The captures carry the memory already: each case has `initial.ram` and
`final.ram`, both lists of `[address, value]`, and `final.ram` is the
initial list plus the bytes the chip wrote. Nothing has to be inferred.

## Specs

- **S1** — The oracle carries the final memory, so the gate compares it. The
  emitted format names the chip's final memory in its own line, and the gate
  compares **every** address that line names: the bytes the chip wrote must
  hold the chip's values, and the bytes the chip left alone must still hold
  theirs. The comparison is through the emulator's public interface, on the
  physical address the capture gives.
- **S2** — The extraction can write **every** capture, not only the sampled
  ones. The command and the file it writes are named in the script's own
  help, and the file is generated: it is not committed, it is gitignored
  beside the oracle, and it is regenerated by the script like everything
  else.
- **S3** — The full gate runs every case in that file and names every
  divergence. A case that disagrees is a **finding**: it is reported with
  the chip's rule as the reason and with the case that shows it, and it is
  never skipped and never allowed quietly. The gate stands aside when the
  file is not there, the way the examples gate stands aside when the
  reference's examples are not there.
- **S4** — The committed gate keeps its shape. The oracle's case count does
  not change (the memory rides on the cases that are already there), the
  pinned count stays exact, the known-divergence list stays empty, and the
  gate still bites: breaking the emulator's rotate carry, its memory write
  or the oracle's coverage must fail it.
- **S5** — The full gate is a research gate, not a unit test.
  `cargo test --workspace` must not depend on a file that is not in the
  repository, so the full gate stands aside on a clean checkout and the
  committed oracle keeps the everyday gate.

## Out of scope

- A count above 62: the captures' harness masks `CL` to six bits, so no
  capture covers it and this unit cannot settle it.
- Any change to a §1.3 cell: the assembler reads that table at compile time.
- The divergences the full set may find: a divergence is a finding, and it
  is named in the log with the case that shows it. It is fixed in this unit
  only when the fix is inside the code the unit already touches; otherwise
  it is the next unit's work, and the plan says so.
- The goldens: they are the reference's, and the reference cannot run here.

## Tasks

- **T1** — The oracle format carries the final memory and the committed gate
  compares it (S1, S4).
- **T2** — The extraction writes every capture into a gitignored file, and
  the script's help names the command (S2).
- **T3** — The full gate runs every case in that file, compares memory as
  well as registers and flags, names every divergence, and stands aside
  when the file is absent (S3, S5).
- **T4** — The unit's findings are in this plan's log: what the full set
  disagreed about, with the case that shows it, and what is left for the
  next unit (S3).

- **L8** (2026-10-23) — What the full set found, **before** the `PUSH SP`
  fix and before L13: **2163 of the 646 000 cases disagree**, in six
  families: 2117 for `PUSH SP`, 28 for `DAA`/`DAS`, 16 for `AAM`/`AAD` with a
  zero immediate (10 `D4` and 6 `D5`), and 2 for `IDIV r/m8`. 2163 = 2153 +
  the ten `D4` cases. **L13 supersedes this entry**: the ten `D4` cases were
  the undefined flags of a divide fault and are not a family, so what
  remains is 36 in three families. The findings are named here with the
  case that shows each one. None of them is in the code this unit touches,
  so every one of them is the next unit's work.
  - **`54` (`PUSH SP`), 2000 cases, plus 117 more under `FF /6` and `FF /7`
    with the `SP` register as the operand** — the chip pushes the stack
    pointer it has **already decremented**. The case: `push sp` with
    `SS:SP = A291:6068` leaves the word `6066h` at `A8976h` and the stack
    pointer at `6066h`; the emulator pushes `6068h`, the value the stack
    pointer had when the instruction started, which is what the 1979 manual
    says. Silicon wins: the chip's rule is the decremented pointer. This is
    the one family the committed gate sees, and it is the reason the
    committed gate is red on 8 cases.
  - **`27` (`DAA`), 17 cases, and **`2F` (`DAS`), 11 cases** — the chip's
    tens correction. The chip applies it when the carry was set or the old
    `AL` was over `99h`; **with the `AF` flag set the old `AL` has to be
    over `9Fh`**. The case that shows the exception: `daa` with
    `AL = 9Ah`, `AF = 1`, `CF = 0` (test hash `3e4193b17b79244f`) leaves
    `AL = A0h` with the carry clear, where the manual's rule
    (`old_AL > 99h`) gives `AL = 00h` with the carry set. The case that
    shows the other side: `daa` with `AL = E9h`, `AF = 1` (test hash
    `011e9e119370e084`) leaves `AL = 4Fh` with the carry set — the tens
    correction **did** fire, because `E9h` is over `9Fh` — and `das` with
    `AL = C4h`, `AF = 1` (test hash `1220e712d95eee40`) leaves `AL = 5Eh`
    with the carry set. The model that fits every one of the 4000 `DAA` and
    `DAS` captures, with no mismatch, is
    `low = (old_AL & 0xF) > 9 || AF` and
    `tens = CF || (old_AL > 0x99 && (!AF || old_AL >= 0xA0))`.
  - **`D5` (`AAD`) with a zero immediate, 6 cases** — the chip does **not**
    fault on a zero divisor. The case: `aad 00h` with `AX = 909Eh` (test
    hash `1998a8307e10fd0b`) leaves `AX = 009Eh` (the high byte clear, the
    low byte untouched) and no interrupt; the emulator raises the type 0
    interrupt and leaves `AX = 909Eh`. **`AAM` (`D4`) with a zero immediate
    is not a family**: the chip faults there, as the emulator does. The
    case: `aam 00h` with `AX = C4C4h` (test hash `ba51cb201fd5e554`) leaves
    `IP = 0400h`, `CS = 0000h` and the stack pointer six bytes below where
    it started, and the flags it leaves there are undefined.
  - **`F6 /7` (`IDIV r/m8`), 2 cases** — the chip faults when the quotient is
    `-128`: the case is `idiv byte [ss:bp-1FFEh]` with `AX = 3354h` (test
    hash `2bf85c12cc23051f`) and the divisor `9Ah` (`-102`), the quotient
    `-128h`, and the chip takes the type 0 interrupt; the emulator computes
    it, because `-128` is inside the range it allows. The manual's wording
    is "larger than 7 bits", so the quotient has to fit in `-127..127`.
